## 10. 2026-10-19 追加調査：レイアウト判定と MIDI ノート数

この節は GitHub 上のファイルを静的に読み取って得た結果。Windows 上での変換実行・MIDI 再生・SNG2S/SNG2GS 実行ファイルの照合は行っていない。

### レイアウト判定の追加確認

`src/Glosa.Core/Smf/SngConverter.cs` の `TryLayout` と同じ主要条件（バージョン別パート数、サイズ表、3つの `headerEnd` 候補、各パートの `used / ctl / idx` 検証）を、GitHub にある v1〜v4 の SNG ファイルのバイト列に適用した。

- v1 `runner.SNG`：`headerEnd=208`、`116`、`114` の全候補が、最初のパートの長さフィールド検証で失敗。
  - `headerEnd=116`：part 1 start=1510、size=1311、`used=0`、`ctl=53248`、`idx=1`、capacity=1153。`used + ctl + idx > capacity` で失敗。
  - `headerEnd=114`：part 1 の `idx=53248` となり capacity を超過。
  - `headerEnd=208`：part 1 の `ctl=1036`、`idx=17920` となり capacity を超過。
- v2 `SHIZUME0.SNG`：`headerEnd=116` と `114` の候補が検証を通過。
- v3 `START__0.SNG`：`headerEnd=208` の候補が検証を通過。
- v4 `BOURREE0.SNG`：`headerEnd=232` の候補が検証を通過。

**結論：** 現行の v1 エラーは、シグネチャやバージョン認識の段階ではなく、レイアウト候補のパート長検証で起きることを静的に再現できた。v1 の形式差、サイズ表の解釈、パートヘッダーの構造差などが候補だが、原因はまだ特定できていない。条件を単純に緩めて通す修正は行わない。

### v2 のノート数差に関する追加分析

対象ファイル:
- SNG: `testdata/ballade/v2/SHIZUME0.SNG`
- 参照 MIDI: `testdata/ballade/v2/sng2gs/SHIZUME0.MID`
- Glosa MIDI: `testdata/ballade/v2/glosa-test-convert/SHIZUME0.mid`

SNG を現行の JMPlayer/Glosa と同じレイアウト前提で静的に読み、各パートの 8-byte ノートレコードを数え、現行 tie 処理と同じ条件で連結されるノートをまとめた結果、Glosa MIDI のノートオン数とパートごとに一致した。

| SNG パート | ノートレコード数（gate > 0） | tie 連結数 | Glosa と一致するノートオン数 |
|---:|---:|---:|---:|
| 2 | 255 | 26 | 229 |
| 3 | 774 | 2 | 772 |
| 4 | 679 | 2 | 677 |
| 5 | 592 | 25 | 567 |
| 6 | 371 | 2 | 369 |
| 7 | 724 | 23 | 701 |
| 8 | 209 | 27 | 182 |
| 9 | 179 | 19 | 160 |
| **合計** | **3,783** | **126** | **3,657** |

この追加照合により、ノートオン数の差の直接原因を特定できた。

| 指標 | 件数 |
|---|---:|
| SNG の gate > 0 のノートレコード | 3,783 |
| うち bit 7（tie／継続フラグ）が立っているレコード | 1,070 |
| bit 7 が立っていないレコード | 2,713 |
| SNG2GS 参照 MIDI の Note-on | 2,713 |
| 現行 Glosa MIDI の Note-on | 3,657 |
| Glosa が参照 MIDI より多く出す Note-on | 944 |

SNG2GS 参照 MIDI の全2,713件は、SNG 内の **bit 7 が立っていないノートレコード**と、音高・ベロシティが一致する。開始時刻は、今回の再照合では reference MIDI tick = source SNG tick + 128 と確認した。Glosa は小節長288 ticksを加えるため、Glosaと参照MIDIの差が160 ticksになる。以前の「source tick = reference MIDI tick + 160」という記録は誤りとして訂正する。参照 MIDI の Note-on 数は、bit 7 が立っていないレコード数と完全一致する。

現行 Glosa の tie 処理は、直前に処理したノートだけを見て、音高と終了 tick が一致した場合に限り連結する。そのため、同じ和音内で別の音が間に入る tie など、多くの bit 7 付きレコードを新しい Note-on として出力してしまう。現行 Glosa は tie 付き1,070レコードのうち126件だけを連結し、残る944件を Note-on として出力している。これは SNG2GS 参照 MIDI とのノートオン数の差944件と一致する。

**結論：ノートオン数の差の直接原因は、Glosa の tie／継続フラグ処理が狭すぎること。** 修正方針は、bit 7 が立ったレコードを新しい Note-on として出さず、同じ音高の継続先 Note-off を正しく延長できるようにすること。実装前に、SNG2GS 参照 MIDI の Note-off tick と複数音の tie 連結を追加照合して、具体的な延長規則を確認する。

開始時刻については、参照MIDIが元SNG tick +128、Glosaが元SNG tick +288で、両出力間に160 ticksの差があると再確認した。なぜ参照MIDIが+128を使うかは未解決。参照 MIDI の生成オプションも未確認なので、オプション依存の差がないかを記録しておく。

### Note-off／tie 延長の追加照合（更新：全2,713件一致）

先の「2,676件一致、37件差」という比較は、直前ノートの終了 tick と tie 開始 tick が完全一致する場合だけを継続とみなしていたため、正しい規則を表していなかった。追加調査で、各パートのノートレコードを元の並び順で処理し、音高ごとに直近の Tie なしノートを保持して、同じ音高の bit 7 付きレコードが現れるたびに、そのノートの終了 tick を当該レコードの start + gate に更新するモデルを検証した。

- Tie レコードと通常ノートの間に別の音高のレコードが挟まっていても、音高ごとの状態を維持する。
- tie の開始 tick と直前ノートの gate 終了 tick が一致することは必須条件にしない。

## 2026-10-19 追加調査：0xFA0表のキーとNote-off相当出力

呼び出し元 `1000:37E4–3844` と補助関数 `3A10` / `3A3F` の実命令を照合し、前回保留していた表フィールドの意味を一段階絞り込めた。

### 呼び出し時のレジスタ対応

`37E4–37F3` は、まず `AL=0x90` をチャンネル番号で補正し（`3B2F`）、次に `AH=現在レコードのkey`、`DL=現在レコードのgate` を設定して `3A3F` を呼び出す。`DH` にはレコードのフラグ `record[7] & 0xC0` が保持される。

### 0xFA0表の構造（確認できた範囲）

- 1エントリは4 byte、最大64エントリ。
- byte `+0` は `DL`、すなわち呼び出し時のgate値を保存する。
- byte `+1` は0で初期化される。
- word `+2` は `AX` と比較される。呼び出し元で `AL=0x90 | channel`、`AH=key` なので、これはMIDI status/channelとkeyを組み合わせた照合キーと解釈できる。格納時は `AL` と `AH` がそれぞれ byte `+2` / `+3` に保存される。
- `3A3F` は照合キー一致のエントリについて、保存gateと現在の `DL` を比較し、条件を満たすとエントリの先頭wordを0にして使用数 `0xF9E` を減らす。
- `DH != 0xC0` の場合、`3A3F` は出力バッファへ `AL`、`AH`、`0` の3 byteを書き込む。ここで `AL` は `0x90 | channel`、`AH` はkeyなので、MIDI上は **Note-on status / key / velocity 0** の形であり、MIDI規則上のNote-offとして機能する出力と判断できる。`DH == 0xC0` では、この3 byte出力をスキップする。

### この結果から言えること／まだ言えないこと

`0xFA0` は単なる「同じ音高の履歴表」ではなく、少なくとも status/channel と key の組み合わせでエントリを検索し、gate値を使って状態を更新するアクティブノート関連表だと確認できた。これにより、チャンネルをまたいだ同音高だけで誤って照合するモデルは不適切である。

ただし、保存gateの比較条件が実際の時間経過やタイ処理全体とどう連携するか、`DH == 0xC0` が出力を抑制する意味、`0x40` の次レコードgate書き換えが参照MIDIのTie延長をどこまで説明するかは、引き続き追跡が必要。これらを確認する前に `SngConverter.cs` は変更しない。


## 2026-10-19 追加調査：gateカウントダウンとNote-off生成の接続

`FUN_1000_3406` の先頭側（`3416–3455`）と、`37E4–3844` のノートレコード処理をつなげて確認した。

- `0xFA0` 表の各エントリ先頭byte（保存gate）は、処理ステップごとに1ずつ減算される。
- 保存gateが0になったエントリでは、表の `+2` / `+3` にあるstatus/channelとkeyを出力し、その後 `0` を出力する。これは `status / key / velocity 0` で、MIDIのNote-offとして機能する。
- そのタイミングで `3D9F` がチャンネル状態表 `0x113E` の該当フラグを解除し、アクティブエントリ数 `0xF9E` も減らす。
- したがって、通常のノート終了は単に次のレコードを見て決めるのではなく、内部表のgateカウントダウンからも発生する。レコード処理中の `3A3F` も同じ表を照合し、既存ノートの状態に応じて終了出力や再登録を制御する。

この構造は、Tie延長を検討するうえで重要である。少なくとも、SNG2S側では「ノート開始時にgateを表へ登録し、各処理ステップで減算し、ゼロ到達時にNote-off相当を出す」という機構が実装されている。ただし、`0x40` フラグ時の次レコードgate書き換えと、v2参照MIDIで観測した延長時刻が全ケースでどう対応するかは、まだ検証を要する。`SngConverter.cs` は変更していない。


## 2026-10-19 追加調査：3A3Fの比較条件と0x40分岐の意味

`3A3F` の命令列を呼び出し元 `37F3–381A` と合わせて再確認し、前回より具体的な制御条件を特定した。

### 3A3Fの比較条件

一致する status/channel + key のエントリが見つかった場合、`3A3F` は保存gate（`[BX]`）と現在レコードのgate（`DL`）を比較する。

- 保存gateが現在gate以上（`savedGate >= currentGate`）なら、エントリを保持し、戻り値の `DL` を1にする。呼び出し元は `JNZ 381F` で通常の新規登録経路をスキップする。
- 保存gateが現在gateより小さい（`savedGate < currentGate`）なら、エントリ先頭wordを0にしてアクティブ数を減らし、戻り値の `DL` を0にする。`DH != 0xC0` なら、同じstatus/channel + keyに対して velocity 0 の終了イベントを出力する。呼び出し元はフラグ条件に応じて、新しいエントリを登録するか、0x40専用処理へ進む。
- `DH == 0xC0` の場合、3A3F内の終了イベント出力は抑制される。呼び出し元も `DH == 0xC0` なら新規ノート状態の登録・Note-on出力をスキップする。

### 0x40専用処理

`3A3F` が一致するエントリを見つけなかった場合、呼び出し元は `DH == 0x40` なら直ちに `3A10` で登録せず、次の条件を検査する。

1. 現レコードの step (`record[2]`) が0。
2. 次レコードの key (`record[8]`) が現レコードの key と一致。
3. 次レコードのフラグ (`record[15] & 0xC0`) が0。

すべて満たす場合、次レコードの gate (`record[9]`) を0に書き換える。これは、8-byteレコードを連続処理するため、`+8/+9/+15` がそれぞれ次レコードのkey/gate/flagsを指すことに注意が必要である。

### Tieモデルへの含意

この命令列からは、`0x40` を単純な「Note-onを出さないTieフラグ」とみなすのは誤りで、少なくとも「同じキーの既存アクティブ状態の有無」「保存gateと現在gateの大小」「次レコードのkey/flags」「step=0」の組み合わせで処理が変わることが分かる。また、既存エントリが見つかり保存gateが現在gate以上の場合、通常経路はスキップされ、gateを単純に加算する動作ではない。

v2参照MIDIで一致したNote-off時刻モデルは引き続き経験的な観測として保持するが、SNG2Sの内部アルゴリズムと完全に同じだとはまだ断定しない。次は、これらの比較条件をSHIZUME0の各レコード列に適用し、どのレコードがgate更新・終了・次レコードgate書換えの各分岐に入るかを検算する。`SngConverter.cs` は変更していない。


## 2026-10-19 追加調査：3A3Fの戻りフラグと呼び出し元分岐

`3A3F` の返り値を、単なる関数戻り値ではなく、呼び出し元 `37F3` 直後の `JNZ 381F` が参照するCPUフラグまで含めて整理した。

- 一致する表エントリがなく、走査が終わる場合、`3A5E` の `XOR AX,AX` が設定した ZF=1 は、後続の `POP` 命令では変更されない。そのため呼び出し元は `JNZ 381F` を通らず、未登録時の分岐へ進む。
- エントリが見つかり `savedGate >= currentGate` の場合、`3A67–3A69` で DL=1 となり、後段の `OR DL,DL` が ZF=0 を設定する。呼び出し元は `JNZ 381F` で通常の新規登録・0x40専用処理をまとめてスキップする。
- エントリが見つかり `savedGate < currentGate` の場合、エントリを解除し終了イベントを出力したうえで DL=0 となる。`OR DL,DL` により ZF=1 となるため、呼び出し元は未登録時と同じ下流分岐へ進む。

このため、`0x40` の次レコード検査は「表にエントリがなかった場合」だけでなく、「一致するエントリがあったが gate 比較で期限切れとして解除された場合」にも実行され得る。ここは前の説明に追加すべき重要な条件である。

### 検証上の注意

この制御フローは逆アセンブルされた命令列から確認できる。一方、個々のSHIZUME0レコードがどの分岐を通るかをデータ上で再現するには、バイナリSNGのレコードを正確なパート境界と時間状態でシミュレートする必要がある。現段階では、v2の参照MIDIとの照合結果と、命令列から分かった制御条件を区別して記録し、両者が同じモデルを支持するかを次段階で検証する。


## 2026-10-19 追加調査：ノート出力ゲートとパート別状態の更新順

`1000:3669–3890` の命令列を前後の処理と合わせて再確認し、ノート出力が「フラグだけ」で決まらない理由を追加で特定した。

### 確認できた処理順

1. `1000:3406` の先頭では、前回までに登録された `0xFA0` のアクティブノート関連エントリを走査し、各エントリの gate byte を1減らす。0になったエントリは status/channel・key・velocity 0 を出力し、チャンネル状態フラグを解除してエントリ数を減らす。
2. その後、ノート／コントローラ／テンポ等のストリームを処理する。ノート側は `0x10DE` から現在のパート内オフセットを読み、1レコードを処理すると4 byte進める。各レコードの時刻差を計算し、次に処理するパートをスケジューリングする。
3. ノートレコード処理では、`record[7] & 0xC0` の分岐より先に `3A3F` を呼び、status/channel + key に一致するアクティブ状態を照合する。そのため、同じフラグ値でも既存状態と gate 比較結果によって後続処理が変わる。
4. `DH != 0xC0` の経路では、`record[4]` から velocity を取り出す。`0x884 + DI` のパート別ワードが0の場合だけ、チャンネル状態を立て、status/channel・key・velocity を出力バッファへ書き込む。その後、同じパート別ワードに key と velocity を保存する。ワードが0でない場合はその3 byte出力を抑制するが、key と velocity の保存自体は行われる。
5. `DH == 0xC0` では、上記の Note-on 相当出力／パート別状態更新を飛ばし、時刻差処理へ進む。

### 解釈上の注意

- `0xFA0` は gate countdown と status/channel + key の照合に使われるアクティブノート関連表である。一方、`0x884 + DI` はパート処理中の出力抑制に関わる別の状態であり、両者を同一の「Tieテーブル」と扱ってはいけない。
- `0x884` のワードが0に戻る全経路は、今回の抜粋だけではまだ特定できていない。したがって、これを正式に「前の音が鳴っている」フラグと命名するのは保留する。
- gate countdown は `3406` の呼び出しごとに進む。ノートレコードの `step` やパート間のスケジューリングとどう対応するかを無視して、レコード列だけを単独でシミュレートするのは不十分である。

### 次の確認

`0x884 + DI` を更新・初期化する全参照を調べ、どのイベント／分岐で0に戻るかを確認する。続いて、パート別スケジューラの時間差計算と `0xFA0` の gate countdown の関係を整理する。SNG2Sの処理モデルが一続きに説明できるまでは `SngConverter.cs` を変更しない。


## 2026-10-19 補足：0x884領域は初期化時にも使用されるため、意味を保留

前節で扱った `0x884 + DI` の全参照を逆アセンブルテキストから検索し、初期化経路も確認した。

- 初期セットアップ `1000:2B25–2B37` は、`0x884 + partIndex*2` が0かを調べ、0ならパートデータ内の byte `+0x26`（別形式では `+0x13` を加工した値）を書き込む。
- ノート処理 `1000:3829–3844` は同じ領域を0判定に使い、条件を満たした場合に key と velocity を保存する。
- このため、当該領域は初期セットアップ由来の値と実行時のノート処理の両方で使われる。単純な「再生中フラグ」や「前の音が鳴っているフラグ」とする説明は根拠不足であり、正式な意味づけを保留する。
- 解析テキスト内で直接確認できた書き込みはセットアップ時とノート処理時に限られる。ゼロへ戻す別経路や、初期値の意味を確定できる定義はまだ見つかっていない。

前節の「0x884はパート別の出力抑制に関係する別状態」という記述は維持できるが、状態の意味は未確定とする。次は初期化元データの形式差と、`0x884` の読み書きが同じ用途を共有する理由を確認する。実装変更は引き続き保留する。


## 2026-10-19 訂正：0x884判定領域と0x788ノート状態領域は別

`1000:3824–3844` のレジスタ遷移を再確認し、前節の表現を訂正する。

- `3829` で一時的に `BX=0x884` として `[BX+DI]` を検査するが、直後の `POP BX` により `BX` は `37E4` で設定した `0x788` に戻る。
- したがって `3842` と `3844` の書き込み先は `0x788+DI` と `0x789+DI` であり、`0x884+DI` ではない。キー／ベロシティの保存先は `0x788` 領域である。
- `0x884+DI` はこのノート処理箇所では読み取り判定に使われる別領域である。初期化時にはパートデータの `+0x26`（別形式では `+0x13` を加工した値）から初期値が設定される。
- ただし、実行時の `DI` はスケジューラ配列 `0x1556` から選ばれた内部スロットを示す。SNGのファイル上のパート番号と常に同じ添字だと仮定してはならない。`0x884` の正確な意味は、初期化値とスケジューラの対応を追うまで未確定とする。

前節の「0x884にkeyとvelocityを保存する」という記述は撤回し、「0x884は出力抑制判定に使われる別領域、key／velocityは0x788に保存」と読み替える。これは解析文書の訂正であり、`SngConverter.cs` の変更ではない。


## 2026-10-19 追加：0x884の初期化後の役割

命令列全体を検索すると、`0x884 + 2*partIndex` への書き込みは初期セットアップ `1000:2B25–2B37` で確認できる。ノート処理 `1000:3829–3844` ではこの値を読み、非ゼロならノート出力の3 byte書き込みを抑制する。一方、`POP BX` によりBXは `0x788` に戻るため、key／velocityの保存先は `0x788+DI` であり、`0x884` ではない。

現時点の逆解析テキストでは、ノート処理ループ内で `0x884` を更新する命令は見つからない。したがって `0xFA0` のgate countdownとは別で、初期化後は固定の出力ゲート／スロット設定値として使われる可能性が高い。ただし、初期化はファイル上のパート順、実行時の添字DIはスケジューラ配列 `0x1556` に由来するため、両者の対応表と `0x788` の読み出し側が未確定である。値の意味は確定せず、引き続き調査する。
