## 4. 今回確定した重要な区別（MIMPIV4）

### mode-1 と mode-2 の分離

- `FUN_1000_0010` の dispatch で、legacy Ballade mode-1 は `FUN_1000_22C4` → `FUN_1000_22FC` に進む。
- mode-2 は `FUN_1000_30E0` に進む。
- `FUN_1000_341E` は `FUN_1000_30E0` 側から呼ばれる。したがって、その special-record pre-scan は mode-2 の処理であり、mode-1 の tempo-record 処理を判断する根拠には使えない（F-150）。
- 追加確認により、`FUN_1000_3543` の直接 caller は `FUN_1000_3240` のみ、`FUN_1000_3240` の直接 caller は `FUN_1000_30E0` のみと判明した。
- したがって `FUN_1000_3543` の per-track event stream 走査も mode-2 branch に属する。これも mode-1 の tempo-record consumer を示す証拠ではない（F-151）。
- この呼び出し関係は PR #50 のブランチ上の FACTS.md に記録されている。PR #50 が未マージである間は、main の文書へ反映済みと扱わない。

### mode-1 側で分かっていること

- `FUN_1000_22FC` は legacy conductor structure の `+0x1C` byte を `0x7BF0` と `0x0440` にコピーする。
- mode-1 driver initializer `FUN_1FF5_1409` は `0x7BF0` から `0x0440` を復元する（F-147）。
- `0x043E` は event-relative offset として使われ、`0x0440` に加算されて timer scheduling に渡る経路がある。
- `FUN_1000_8888` は text command parser から `0x043E` を設定する。`FUN_1000_C6A4` は keyboard timing control によって調整する。`FUN_1000_A3BB` は relative offset を reset して base のみを schedule できる（F-148/F-149）。
- binary SNG conductor tempo-record の second word から `0x043E` への dataflow は確認されていない。
- `FUN_1000_2D27` は mode-1 loader `FUN_1000_22FC` から条件付きで呼ばれ、Program Change rewrite を行うことは確認済み。ただし tempo-record consumer かどうかは未確定。
- 現時点で MIMPIV4 が tempo record を無視すると結論してはならない。consumer が未発見という状態である。

## 5. 次に行う調査 — T-016

**目的:** MIMPIV4 legacy Ballade mode-1 の実際の再生処理経路を追跡し、conductor tempo record の読み取り箇所と、その値が timer parameter または event interval に反映される箇所を特定する。

優先する調査順:

1. `FUN_1FF5_1409` の mode-1 初期化後に続く event processing / scheduling の呼び出し先を追う。
2. mode-1 の event loop から、イベントレコードの読み取り、次イベントまでの時間計算、timer 再設定へ至る dataflow をたどる。
3. conductor tempo-record の second word がどの関数・変数に読み込まれるかを検索する。既知の `0x043E` / `0x0440` だけに探索を限定しない。
4. `FUN_1000_2D27` は mode-1 branch 内の候補として調べるが、Program Change rewrite 以外の役割を根拠なく推定しない。
5. mode-2 の `FUN_1000_3240` / `FUN_1000_341E` / `FUN_1000_3543` は、mode-1 の根拠として再利用しない。
6. 静的解析だけで consumer を特定できない場合は、既知の tempo-changing SNG を使った runtime trace で、tempo record の直前・直後の timer / scheduler state を比較する。trace を実施していない段階では、実行時挙動を確認済みと記載しない。

### T-016 の完了条件

- mode-1 で conductor tempo record を読む関数と読み取り元フィールドが特定されている。
- 読み取った値が timer base、event-relative interval、または別の scheduler state のどれにどう反映されるか、呼び出し関係とデータフローで説明できる。
- mode-2 branch の処理を根拠から除外している。
- 静的解析と runtime trace / playback の検証段階を明確に区別している。
- consumer が見つからない場合は、調査した範囲と否定できる範囲を限定して記録し、「tempo record を無視する」と一般化しない。
