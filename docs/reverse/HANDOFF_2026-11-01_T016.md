## 3. 直近の調査結果（2026-11-01）

### 3.1 0x043E の書き込み元

MIMPIV4 の完全な静的解析 export で 0x043E の直接参照を調査した。確認できた主な書き込み経路は次のとおり。

| 関数 | 確認できた処理 |
|---|---|
| `FUN_1000_8888` | テキストコマンドから値を解析して設定 |
| `FUN_1000_A3BB` | 0 にクリア |
| `FUN_1000_C6A4` | キー操作による増減 |
| `FUN_1FF5_1409` | mode 1 初期化時のクリア |

さらに `FUN_1000_8888` の呼び出し元 `FUN_1000_7E55` を追跡し、`@` で始まるテキストコマンドを解析・振り分ける処理であることを確認した。

したがって、現時点で確認できた `0x043E` の設定経路は、バイナリ SNG の tempo record を直接読む経路ではなく、テキストコマンド／キー操作等の経路である。

**重要な限定:** これは「0x043E について確認できた範囲」の結論である。MIMPIV4 が SNG tempo record を無視している、あるいは再生テンポを変更しない、という結論ではない。別の変数、間接書き込み、別のタイマー経路を使っている可能性が残る。

### 3.2 0x0440 / 0x7BF0 の mode 1 経路

これまでの調査で確認した内容:

- `FUN_1000_0010` は legacy Ballade loader 経路で `0x016E = 1` を設定し、`FUN_1000_22C4` → `FUN_1000_22FC` を呼ぶ。
- この loader は legacy conductor header の `+0x1C` byte を `0x7BF0` と `0x0440` にコピーする。
- `FUN_1FF5_1344` は mode 1 の場合 `FUN_1FF5_1409` を選び、`0x0440` を `0x7BF0` から復元する。
- 他の mode 2〜4 の初期化関数にある `0x0438 → 0x0440` コピーを、mode 1 の経路と混同しないこと。

`0x0440` は mode 1 の timer base として追跡されている。一方、後続の SNG tempo record が再生中にこの値や別の timer input をどう更新するかは未解決。

### 3.3 0x043E と 0x0440 の役割の区別

既知のテキストコマンド経路では、`FUN_1000_8888` が `0x043E` に相対値を格納し、`0x043E + 0x0440` を `FUN_1FF5_0DE1` に渡す。

- `0x0440`: mode 1 の timer base として追跡されている値
- `0x043E`: テキストコマンドやキー操作で変更される event-relative offset として確認された値
- `FUN_1FF5_0DE1`: 要求値を `0x3390` に格納し、ゼロを 1 に正規化する処理
- `FUN_1FF5_0DFA`: CX 入力から timer hardware divisor を計算し、timer 関連 I/O port を設定する処理

この既知のテキストコマンド経路だけでは、バイナリ SNG tempo record の second word が timer input に到達することは証明できない。

## 4. T-016 の現在の課題

**目的:** MIMPIV4 がバイナリ SNG の tempo record を読み込み、再生中のタイマー間隔・再生テンポへ反映する経路を特定する。

次に調べる対象:

1. SNG の binary tempo record を読み込む parser / loader の関数と、その呼び出し元を特定する。
2. tempo record の各フィールド（特に second word）が、どの変数・バッファへ格納されるかを追う。
3. 初期化時だけでなく、再生中の record 処理で timer base、timer divisor、scheduler interval、その他の時間管理変数が更新されるか確認する。
4. `0x0440`、`0x0438`、`0x7BF0` 以外の timer 関連変数について、直接参照・間接参照・書き込み元・読み取り元を一覧化する。
5. binary tempo record の読み込みから timer hardware への反映まで、関数呼び出しとデータフローを連続してつなぐ。
6. 静的 export で経路が欠落している場合は、その欠落を明記し、runtime trace が必要な未解決事項として残す。

### 調査の進め方

- まず既存の private MIMPIV4 export と現在の FACTS / LOG を再確認する。
- 「timer」「tempo」「countdown」「interval」などの名前だけで役割を断定しない。実際の read/write と呼び出し元・呼び出し先を追う。
- 変数ごとに、アドレス、サイズ、全書き込み元、全読み取り元、初期化経路、再生中の更新候補を記録する。
- binary tempo record の parser から timer 更新関数までのデータフローがつながらない限り、「tempo record がタイマーに反映される」と断定しない。
- 0x043E が binary record から更新されていないという今回の結果を、他の変数にも一般化しない。

## 5. 確認済みの事実・推測・未解決事項

### 確認済み（静的解析）

- PR #46 は上記 merge commit でマージ済み。
- 0x043E の既知の直接書き込み元は、テキストコマンド設定、クリア、キー操作、mode 1 初期化時クリア。
- `FUN_1000_8888` は `@` で始まるテキストコマンドの解析経路から呼ばれる。
- mode 1 の初期 timer base は legacy loader の `+0x1C` byte から `0x7BF0` / `0x0440` に設定され、mode 1 driver initializer が `0x7BF0` から `0x0440` を復元する。
- 既知の `0x043E` 経路は、binary SNG tempo record の直接処理とは別の経路である。

### 未解決

- binary SNG tempo record を実際に読み込む MIMPIV4 の関数・呼び出し元。
- tempo record の値が再生中にどの変数へ格納されるか。
- その値が timer interval / divisor / scheduler に反映されるか。
- mode 1 の全 timer 関連変数とその更新経路。
- 静的解析で見えない間接書き込み・alias・実行時分岐の有無。
- 実際の MIMPIV4 再生時に tempo record が反映されるか（runtime trace / 実再生による確認）。

### 推測として扱うこと

- 0x043E 以外の変数が tempo record を受け取る可能性。
- timer base と再生中の可変 interval が別々に管理されている可能性。
- 別の scheduler / timer driver 経路を通じて tempo record が反映される可能性。

これらは調査候補であり、事実として記録しない。

## 7. 作業・変更時のルール

1. **安全性チェックで問題が出た場合は PR 方式を使う。** main への直接 push / 直接更新を避け、専用ブランチで変更し、PR の CI と差分を確認する。
2. 安全性チェックが出るかどうかは状況によって異なる。チェックが出ない場合でも、重要な reverse 文書の変更は原則 PR でレビュー可能にする。
3. PR の CI が成功したことを確認してからマージする。CI 未確認・失敗時にマージ済みと扱わない。
4. ユーザーがマージを明示的に依頼していない場合、PR 作成とマージを混同しない。マージ前に結果を報告する。
5. converter / production code / tests は、根拠が揃うまで変更しない。解析目的の docs-only 変更と実装変更を分離する。
6. private SNG/MID fixtures、private MIMPIV4/SNG2S export、機密性のあるデータを public repo にコピーしない。公開 docs には必要な結論と参照可能な根拠だけを記載する。
7. 各 FACTS は静的解析、raw-byte inspection、reference MIDI comparison、runtime trace、実再生を区別して記録する。
8. 直接参照が見つからないことは「検索範囲内で見つからなかった」と表現する。間接参照や alias の可能性を排除したと書かない。
9. 関数名や変数名から意味を推測しない。命令列、引数、read/write、caller/callee を確認する。
10. F-ID は既存最大 ID の次を使い、欠番を再利用しない。ID 変更時は参照先を同じ変更内で更新する。
