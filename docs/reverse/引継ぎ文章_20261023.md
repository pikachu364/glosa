# Glosa Ballade SNG 調査・実装 引継ぎ文書

更新日：2026-10-23

## 1. 目的と現在の方針

Ballade 系 SNG の v1〜v4 を調査し、Glosa の変換結果を参照実装・参照 MIDI・テストと照合する。調査では、確認済みの事実、仮説、未検証の挙動を区別する。未解明の挙動を推測で埋めたり、未実施の作業を完了扱いしたりしない。

**直近の優先方針：**
- まず Windows の開発環境を確認し、Glosa をローカルで build/test できる状態にする。
- その後、SNG v2〜v4 を少数の代表ファイルで検証する。いきなり大量の SNG を試さない。
- v2〜v4 では、SNG2S と JMPlayer の処理の違いが判明しつつある。差分を版別・処理別に整理し、実データで確認できた項目から検証する。
- Ballade v1 のテンポ内部処理は、いったん優先度を下げる。調査記録と回帰テストは維持し、v2〜v4 の整理を妨げない。これは v1 対応を放棄する意味ではない。
- 内部仕様の完全解明を待ってからテストするのではなく、環境が整ったら代表データでテストし、観測された差に絞って調査する。

v2〜v4 の主な難しさは、単純に SNG の版が異なることだけではなく、**SNG2S と JMPlayer の処理・解釈が異なること**。違いが判明しつつあるため、同じ挙動だと仮定せず、次の軸で表に整理する。

1. ファイルの読み取りと版別レイアウト
2. テンポ値の解釈・tempo event の生成または再生時の消費
3. ノート、Tie、step、gate、nudge と tick の扱い
4. conductor の小節数と各パートの終端
5. トラック・チャンネル・イベント順序
6. 不正・欠損・内部整合性のないファイルへの対応

各差分は「確認済み」「有力な説明」「未確認」に分ける。SNG2S の MIDI 出力処理と MIMPIV4 の実再生処理は別物として扱い、同じテンポ式を使うと決めつけない。

### テンポスライダーについて

JMPlayer の形式資料には、SNG2S にテンポ値 1〜127 を与えた測定結果として、値は BPM そのものではなくスライダー位置で、次の式に沿うと記録されている。

`BPM = 2v - ceil(v / 8)`

例：61 → 114 BPM、72 → 135 BPM、91 → 170 BPM。資料では、3/4 拍子で同じ値から BPM が 1 高くなるのは SNG2S の丸めと説明している。実際のドライバーはタイマーを設定するため拍子を参照しない、という分析である。

この式は SNG2S の測定・変換挙動として扱う。MIMPIV4 の再生中テンポ計算や Glosa の全バージョンの仕様へ、追加根拠なしに一般化しない。

### 参照と一致しないファイル

JMPlayer の資料では、SNG2S と一致しない2曲について次の説明がある。

- `MAGICAL0.SNG`：126 KB で切れたファイルで、リズムパートが半分欠けている。他の9パートは再生できるよう、末尾ブロックのみ EOF 越えを許す扱い。
- `3X3EYES2.SNG`：SNG2S と合わせるには途中に 10,029 ticks を挿入する必要があるが、ファイルにその指示がない。conductor は97小節、各パートは96小節で内部的に整合する一方、SNG2S の出力は148小節になるため、資料では推測による補正を避けている。

このような例を Glosa の通常動作に合わせるために、根拠のない時間挿入や長さ補正を実装しない。ファイル異常・参照処理固有の挙動・Glosa の不具合を区別して記録する。

## 4. 調査データの置き場（private リポジトリ）

SNG の原本、参照コンバーターの出力 MIDI、Glosa の比較用出力 MIDI、逆解析資料は、公開リポジトリ `pikachu364/glosa` ではなく、専用の private リポジトリ `pikachu364/glosa-private-data` に置いてある。この引継ぎ文書を読む作業者には同リポジトリの閲覧権限が付与されている前提とし、ここを調査データの正本として使用する。

### データ全体

[Ballade 調査データのルート（testdata/ballade）](https://github.com/pikachu364/glosa-private-data/tree/main/testdata/ballade)

ここには Ballade SNG のバージョン別に分けた比較用データがある。各バージョンのフォルダーには、基本的に次の3種類のファイルを置いている。

- **元の SNG ファイル**：比較・変換の入力となるデータ
- **SNG2S で変換した MIDI（MID）**：参照コンバーターの出力
- **開発中の Glosa で変換した MIDI（MID）**：Glosa の出力。SNG2S の出力と比較して差分を調べるために使う

実際に存在するファイル名や収録状況は、対象のバージョン別フォルダーを開いて確認する。すべてのフォルダーに必ず同じファイルが揃っていると決めつけない。比較時は、同じ入力 SNG に対応する2つの MID を選び、対象ファイル名・変換条件・Glosa の commit/branch を記録する。

- 調査データの正本は上記 private リポジトリとする。アクセス権の再確認を通常の作業手順には含めず、実際にアクセスエラーが発生した場合に限って個別に対処する。

- SNG2S の出力を「唯一の正解」と先に決めず、SNG2S・JMPlayer・Glosa のどの挙動を比較しているかを明確にする。

## 6. v1：現状維持・一時保留

v1 のレイアウト候補は次のとおり。これは静的解析と fixture の整合に基づく。

- `runner.SNG` は 85,897 bytes
- `tableEnd = 114`、legacy `headerEnd = 116`
- part 1 start = 1510
- block size = `entry + 80`
- length fields = `+115 / +117`
- 13 個の相対 seek 値 = `+119..+143`
- note record start = `+145`
- このモデルで runner の Note-on 3,295 件、Note-off 3,295 件を参照と照合した記録がある

`SngConverter.cs` には `ReadLegacyV1Tempi()` があり、公開テスト `BalladeV1RunnerProducesReferenceTempoEvents()` は参照値 500000 / 869000 / 869565 µs/qn の byte sequence を検査する。 `BalladeV1KeepsDefaultTempoWhenTempoStreamIsUnchanged()` は変化しない tempo stream の既定値維持を検査する。これらは特定 fixture と検査範囲の結果であり、v1 全体の完全互換を意味しない。

v1 のテンポ参照 `runner.MID` は tick 0 = 500,000、tick 8 = 869,000、tick 192 = 869,565 µs/qn。SNG2S の静的解析では raw tempo 37 と base tempo 120 から 69 BPM、整数演算経路から 869000 と 869565 が得られる。一方、tick 8 にイベントが出るまでの pending-delta / absolute-tick の因果関係、`0x6EE` の初期値、setup SysEx producer と payload の対応、参照 MIDI の実際の SNG2S オプションは未確定。

## 7. MIMPIV4 再生テンポ

静的解析で確認された timer 初期化・割り込み関連の経路：
- `FUN_1FF5_1344`：driver dispatch
- 選択された setup 分岐で `0x0438 → 0x0440` のコピー
- `FUN_1FF5_0D61`：INT 8 handler 設定
- `FUN_1FF5_0DFA`：timer divisor 計算と I/O port 書き込み

ただし、SNG tempo record の第2 word が再生中に `0x0438`、`0x0440`、`0x7BF0` を更新する経路は未確認。次に調べる場合は、初期化経路を再調査するのではなく、再生レコードの parser/caller と再生中の global 書き込みを追跡する。必要な静的データがなければ、その制約を記録し runtime trace が必要と明示する。
