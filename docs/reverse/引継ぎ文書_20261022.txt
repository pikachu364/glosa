3. jmplayer の v1 読み込み失敗：現在までの重要な発見

jmplayer の sngmidi.cpp の buildLayout() は、SNG バージョンごとのパート数を認識する。

* v1/v2/v3：10パート
* v4：16パート

テーブル開始位置は 0x46。v1 の場合は11個の little-endian 32-bit エントリーで、テーブル終端は 0x72。v1 の設定領域は2バイトなので、ヘッダー終端候補は 0x74。

jmplayer は tableEnd + 94、tableEnd + 2、tableEnd の候補を試すため、v1 の tableEnd + 2 自体は候補に含まれている。

問題は、その後のパート構造を後続版の形式で一律に検証すること。

jmplayer は各バージョンに対し、次のような後続版のオフセットを使う。

* パートサイズ：テーブル値 +81
* used length：+112
* controller length：+114
* index：+116
* パートストリーム開始：+158

一方、Glosa の v1 専用パーサーと、SNG2S/MIMPIV4 の旧版解析は異なる構造を示す。

* パートサイズ：テーブル値 +80
* used length：+115
* controller length：+117
* 13個の相対 seek 値
* ノートストリーム開始：+145

runner.SNG では、正しい v1 ヘッダー終端候補は 0x74、part 1 開始位置は byte 1510。jmplayer の後続版オフセットで検証すると容量チェックに失敗する。別 fixture の TEST.SNG でも同様に3候補すべてが失敗する。

これにより、jmplayer のソース上では buildLayout() が有効な v1 layout を受理できず、toMidi() が空の QByteArray を返す経路として説明できる。

ただし、これはソースと実データの静的照合。jmplayer を実行してエラーダイアログまで再現したわけではない。

5. Tempo slider の重要な仕様

jmplayer のドキュメントに記載：

BPM = 2v − ceil(v / 8)

例：

* 61 → 114 BPM
* 72 → 135 BPM
* 91 → 170 BPM

これは次の式と同じ。

floor(120 * v / 64)

SNG2S の FUN_1000_3406 の逆解析にも、raw value と base tempo を乗算し、0x40 で整数除算する計算がある。結果は1〜480に制限される。base tempo が120なら jmplayer の slider 曲線と一致する。

重要な訂正： 現在の v1 conductor parser が読んだ 37 は step/delay の候補値であり、slider value と確定していない。したがって「37 → 69 BPM が runner.SNG の slider value」という以前の推定は未証明。これを事実として扱わないこと。

参照 MIDI には以下の tempo meta が記録されているとの調査記録がある。

* tick 0：500000 µs/quarter
* tick 8：869000 µs/quarter
* tick 192：869565 µs/quarter

869000 と869565は69 BPMに関連する整数除算の結果として説明できるが、どの SNG レコードがそれぞれを生成し、なぜその tick に置かれるかは未解決。tempo 値とノート tick のスケジューラは別々に調査すること。

3/4 の +1 BPM 問題

jmplayer の説明では、同じ slider value でも3/4曲は SNG2S 出力 MIDI 上で1 BPM高くなる場合があり、SNG2S 独自の丸めと説明されている。実際の再生タイマーは拍子を知らないので、タイマー向けの基本曲線は一つと考えられる。

この +1 BPM を v1 ノート tick 変換へ混ぜないこと。SNG2S の MIDI export 時の丸め問題として独立させる。

現時点で、プライベート fixture tree 内に3/4の参照 MIDI が確認できていない。実データなしで補正を実装しないこと。

6. その他の互換性問題

jmplayer の仕様メモには、2曲が SNG2S と一致しない理由として次が挙げられている。

* MAGICAL0.SNG：ファイルが約126KBで途切れ、リズムパートが欠けている。
* 3X3EYES2.SNG：SNG2S と一致させるには途中に10,029 ticksを挿入する必要があるが、ファイルに根拠がなく、各パートの小節数も自己整合している。

これらは v1 の基本変換が正しいかという問題とは切り離す。破損ファイルの例外対応を先にやらない。
